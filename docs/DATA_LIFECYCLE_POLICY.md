# 담당 도메인 데이터 생명주기 정책

작성일: 2026-08-14

## 목적

공지사항, 전자결재, 학생관리, 강의관리, 출결관리의 데이터를 플랜별 기능 차등과 분리해서 관리한다. 이 문서는 해당 담당 범위의 발표·운영 설계 기준이며, 다른 팀원이 맡은 도메인에 자동 적용되는 전사 정책이 아니다. 마감 범위에서는 새 화면을 늘리지 않고, 현재 구현을 유지하면서 설명할 수 있는 생명주기 기준만 둔다.

## 핵심 원칙

1. 플랜 차등은 보관기간 자체보다 사용량과 용량에 둔다.
   - 첨부파일 저장 용량
   - SMS 월 발송량
   - AI 토큰 사용량
   - 공지 삭제 유예 기간
   - 데이터 동기화 작업 결과 이력
2. 전자결재, 출결, 강의 이력은 업무 증빙과 운영 정합성을 위한 기본 기록으로 본다.
3. 학생 개인정보와 AI 임시 데이터는 목적이 끝나면 짧게 삭제하거나 마스킹한다.
4. RDS는 데이터의 상태와 보존기한을 관리한다.
5. S3는 실제 파일 객체의 저장 계층과 삭제 시점을 관리한다.

## RDS 역할

RDS는 "데이터를 지금 업무 화면에 보여줄지, 삭제 유예 상태로 둘지, 장기 보관할지, 삭제 또는 익명화해도 되는지"를 판단하는 기준을 가진다.

향후 생명주기 컬럼이 필요해지면 아래 값을 도메인별로 선택 적용한다.

| 필드 | 의미 |
| --- | --- |
| `status` | `ACTIVE`, `ENDED`, `ARCHIVED`, `DELETED`, `ANONYMIZED` 같은 업무 상태 |
| `deleted_at` | 사용자가 삭제를 요청한 시각 |
| `archived_at` | 일반 조회에서 분리해 장기 보관 상태로 전환한 시각 |
| `retention_until` | 자동 정리, 삭제, 익명화 판단 기준 시각 |
| `legal_hold` | 분쟁, 감사, 중요 증빙으로 자동 삭제에서 제외할지 여부 |
| `anonymized_at` | 개인정보성 필드를 마스킹 또는 익명화한 시각 |

현재 마감 범위에서는 모든 도메인에 이 컬럼을 즉시 추가하지 않는다. 이미 구현된 `deleted_at`이나 상태값을 우선 사용하고, 실제 화면 또는 배치 요구가 생기는 도메인부터 추가한다.

## S3 역할

첨부파일과 임시 파일은 RDS에 직접 저장하지 않고 S3 객체로 분리한다. RDS는 file id, 소유 도메인, 업무 상태, 보존기한을 관리하고 S3는 Lifecycle 정책으로 비용과 삭제 시점을 관리한다.

| 파일 성격 | 보관 정책 |
| --- | --- |
| 전자결재 첨부파일 | 업무 증빙이므로 장기 보관 대상. 일정 기간 후 저비용 스토리지 또는 Glacier 계열로 전환하고, 보존기한 만료와 `legal_hold=false` 확인 후 삭제 |
| 공지사항 첨부파일 | 공지 상태를 따른다. 삭제된 공지는 삭제 유예 기간 동안 유지하고, 최종 정리 시 함께 삭제 |
| AI 업로드 원본, 프롬프트/응답 원문, 중간 로그 | 개인정보 위험이 크므로 저장하지 않거나 7~30일 안에 삭제 |
| 데이터 동기화 원본/결과 파일 | 작업 검증에 필요한 짧은 기간만 보관하고, 결과 이력은 플랜별 기간 안에서 관리 |
| RDS 장기 보관 export | 자동 백업을 장기 보관 수단으로 보지 않고, 필요한 경우 스냅샷 export를 S3에 저장한 뒤 저비용 보관으로 전환 |

## 저장 데이터 인벤토리

현재 담당 범위에서 DB와 S3에 실제로 남는 데이터는 아래처럼 나뉜다.

### 공통 파일/S3

| 위치 | 데이터 | 의미 | 정책 |
| --- | --- | --- | --- |
| DB `file_metadata.id` | `fileId` | 공지, 결재, 템플릿, 메신저 같은 도메인이 파일을 가리킬 때 쓰는 내부 참조 키 | 단독으로 삭제하지 않고 소유 도메인의 첨부 연결 상태를 따른다 |
| DB `file_metadata.object_key` | S3 object key | 실제 파일이 S3 버킷 안에서 저장된 경로. 예: `tenants/{tenantId}/files/{UUID}-{파일명}` 계열 | 다운로드/삭제 시 S3 객체를 찾는 기준 |
| DB `file_metadata.content_type` | MIME type | `application/pdf`, `image/png` 같은 파일 형식 | 다운로드, 미리보기, Content-Type 응답에 사용 |
| S3 | 실제 파일 객체 | 첨부파일 원본 | 어떤 도메인에서도 더 이상 참조하지 않을 때 파일 모듈이 삭제 |

`file_metadata`는 파일 원본을 들고 있는 테이블이 아니라 S3 객체를 찾기 위한 메타데이터다. 실제 사용자 표시용 파일명은 공지의 `notice_attachment.file_name`처럼 각 도메인의 첨부 연결 테이블에 저장한다.

### 공지사항

| 위치 | 데이터 | 의미 | 정책 |
| --- | --- | --- | --- |
| DB `notice` | 제목, 본문, 작성자, 고정 여부, 조회수, 생성/수정일, `deleted_at`, `retention_until` | 공지 본문과 화면 표시 기준 | 삭제 요청 시 일반 조회에서 숨기고, 유예 기간 만료 후 정리 |
| DB `notice_attachment` | `notice_id`, `file_id`, `file_name` | 공지와 파일 메타데이터의 연결, 사용자에게 보여줄 첨부파일명 | 공지 최종 정리 시 연결 삭제 |
| DB `notice_read` | `notice_id`, `user_id`, `read_at` | 읽음 여부와 조회/읽음 집계 기준 | 공지 최종 정리 시 먼저 삭제 |
| S3 | 공지 첨부파일 원본 | 실제 첨부파일 내용 | 연결 삭제 후 다른 도메인 참조가 없을 때 삭제 |

정리 순서는 읽음 기록, 첨부 연결, 공지 본문 순서다. 첨부 `fileId`는 DB 정리 커밋 이후 파일 모듈로 넘기고, 파일 모듈이 공지·결재·템플릿·메신저 어디에서도 참조하지 않는지 확인한 뒤 S3 객체와 `file_metadata`를 삭제한다.

### 학생관리

| 위치 | 데이터 | 의미 | 정책 |
| --- | --- | --- | --- |
| DB `student` | 이름, 학년, 학교, 학생 연락처, 학부모 연락처, 메모, 생성/수정일, `deleted_at` | 재원생 관리와 상담에 필요한 개인정보 | 삭제 시 소프트 삭제 후 30일 경과 시 정리 |
| DB `student_enrollment` | 학생-강의 연결, 상태, 등록일, 종료일 | 수강 이력과 강의별 수강생 목록 기준 | 학생 최종 정리 시 수강 이력부터 삭제 |
| S3 | 없음 | 학생관리 도메인은 파일 원본을 저장하지 않음 | S3 생명주기 대상 아님 |

학생 개인정보는 플랜 혜택으로 장기 보관을 약속하지 않는다. 목적이 끝나면 삭제 또는 마스킹하는 쪽이 자연스럽다.

### 강의관리

| 위치 | 데이터 | 의미 | 정책 |
| --- | --- | --- | --- |
| DB `lecture` | 강의명, 수업 유형, 학년, 시즌/과목/선생님/교실 정보, 수강료 정보, 생성/수정일, `deleted_at` | 수강, 출결, 매출 이력의 기준 정보 | 삭제 시 소프트 삭제하고 오래됐다는 이유만으로 자동 하드 삭제하지 않음 |
| DB `lecture_schedule` | 요일, 시작 시간, 종료 시간 | 강의 시간표와 시간 충돌 검사 기준 | 강의와 함께 관리 |
| DB `term`, `subject`, `classroom` | 시즌/과목/교실 마스터 | 강의 등록 시 이름 기반 생성/재사용 | 운영 마스터 데이터로 유지 |
| S3 | 없음 | 강의관리 도메인은 파일 원본을 저장하지 않음 | S3 생명주기 대상 아님 |

강의 데이터는 종료 강의 조회 기간을 플랜 혜택으로 팔기보다, 기본 운영 이력으로 보관하는 쪽이 맞다.

### 출결관리

| 위치 | 데이터 | 의미 | 정책 |
| --- | --- | --- | --- |
| DB `attendance_entry` | 강의, 학생, 날짜, 출결 상태, 기타 사유 메모 | 강의별 출결 기록과 학부모 응대 기준 | 업무 이력으로 보관하고 자동 하드 삭제하지 않음 |
| DB `message_template` | 템플릿 이름, 출결 상태, 문자 본문, 작성자, 생성/수정일 | 출결 상태별 안내 문자 원문 | 템플릿 설정 데이터로 관리 |
| DB `resource_usage_event` | `SMS`, `rollcall-attendance-sms`, 성공 발송 건수 | 월별 SMS 사용량 산정 기준 | 발송량 집계용으로 보관 |
| S3 | 없음 | 출결관리 도메인은 파일 원본을 저장하지 않음 | S3 생명주기 대상 아님 |

실제 SMS 발송 때 치환된 문자 본문, 학부모 연락처, 학생별 발송 원문은 별도 장기 이력으로 저장하지 않는다. 출결 엑셀 다운로드도 요청 시점에 byte 응답으로 생성하고, DB나 S3에 파일로 저장하지 않는다.

## 플랜별 차등 기준

플랜 차등은 민감정보나 업무 기본기록의 보관기간을 무작정 늘리는 방식이 아니라, 사용량과 용량처럼 비용에 직접 연결되는 항목에 둔다.

| 항목 | 현재 마감 범위 | 플랜 차등 방향 |
| --- | --- | --- |
| 첨부파일 | `file_metadata`와 S3 객체로 분리 저장 | 제공 용량 확대 |
| SMS | 성공 발송 건수를 월별 사용량으로 기록 | 월 발송량 확대 |
| AI 토큰 | AI 토큰 사용량을 월별 사용량으로 기록 | 월 사용량, 대용량 처리, 재분석 횟수 확대 |
| 공지 삭제 유예 | 삭제 후 30일 동안 일반 조회에서 숨김 처리한 뒤 정리 | 필요 시 삭제 유예 기간 확대 |
| 전자결재 문서/이력 | 플랜과 무관하게 업무 증빙으로 보관 | 보관기간 차등 없음 |
| 강의/출결 기록 | 플랜과 무관하게 운영 이력으로 보관 | 보관기간 차등 없음 |
| 학생 개인정보 | 목적 종료 후 삭제 또는 마스킹 | 보관기간 차등 없음 |
| AI 임시 데이터 | 저장하지 않거나 7~30일 안에 삭제 | 보관기간 차등 없음 |

## 전자결재 보관기간과 삭제 방식

전자결재는 증빙성이 있으므로 플랜별로 보관 여부를 나누지 않는다. 다만 실제 법정 보존기간은 업종, 문서 성격, 회사 정책에 따라 달라질 수 있으므로 아래 값은 발표와 구현 설계를 위한 운영 기준으로 둔다.

| 데이터 | 권장 보관기간 | 보관 이후 처리 |
| --- | --- | --- |
| 결재 문서 본문 | 완료/반려/취소 후 5년 | 일반 조회에서 분리하고 `ARCHIVED` 상태로 전환 |
| 결재선 | 결재 문서와 동일 | 문서보다 먼저 삭제하지 않음 |
| 승인/반려 이력 | 결재 문서와 동일 | 감사 추적을 위해 문서와 함께 보관 |
| 결재 첨부파일 | 결재 문서와 동일 | S3 저비용 스토리지로 전환 후 만료 시 삭제 |
| 중요 증빙/분쟁 가능 문서 | 10년 또는 `legal_hold` 해제 전까지 | 자동 삭제 대상에서 제외 |

보존기간이 끝났다고 즉시 완전 삭제하지 않고 아래 순서로 처리한다.

```text
IN_PROGRESS
-> APPROVED/REJECTED/CANCELED
-> retention_until 도달
-> legal_hold 확인
-> ARCHIVED 전환
-> 최종 만료 시 첨부파일 삭제, 개인정보성 필드 익명화 또는 최소 감사 정보만 유지
```

예를 들어 휴가 신청 결재가 승인되면 RDS에는 문서 상태, 결재선, 승인 시각, 승인자, 보존기한을 남긴다. 첨부파일은 S3에 두고 90일 이후 저비용 스토리지로 이동시킬 수 있다. 5년이 지나면 일반 화면에서는 숨기고, 분쟁이나 감사 대상이 아니라면 최종 만료 시 첨부파일을 삭제하고 개인정보성 본문은 익명화한다.

## AI 데이터 보관 기준

AI 데이터는 유료 플랜이라고 오래 보관하지 않는다. 결재 증빙으로 확정된 최종 결과인지, 처리 과정에서만 쓰인 임시 데이터인지에 따라 다르게 관리한다.

| AI 데이터 | 보관 정책 | 이유 |
| --- | --- | --- |
| 업로드 원본 파일 | 7~30일 후 삭제 | 개인정보와 문서 원문이 포함될 수 있음 |
| 프롬프트/응답 원문 | 저장하지 않거나 7~30일 후 삭제 | 개인정보와 업무 내용이 그대로 남을 수 있음 |
| AI 분석 중간 로그 | 저장하지 않거나 7~30일 후 삭제 | 장애 분석 외 장기 보관 필요가 낮음 |
| 단순 미리보기 결과 | 30~90일 후 삭제 | 결재 증빙으로 확정된 데이터가 아님 |
| 결재 문서에 반영된 최종 요약/추출 결과 | 결재 문서와 동일하게 보관 | 결재 판단 근거가 되면 문서의 일부로 봄 |

즉 AI 원본과 중간 산출물은 짧게 삭제하고, 최종 결과가 결재 문서에 저장된 경우에만 결재 보존 정책을 따른다. 이 기준은 플랜 차등보다 보안 등급을 우선한다.

| S3 객체 유형 | 예시 경로 | Lifecycle 예시 |
| --- | --- | --- |
| 전자결재 첨부파일 | `approval/{documentId}/{fileId}` | 90일 후 저비용 스토리지, 1년 후 Glacier 계열, 보존기간 만료 후 삭제 |
| 공지사항 첨부파일 | `notice/{noticeId}/{fileId}` | 삭제 유예 기간 동안 유지, 유예 기간 만료 후 삭제 |
| 중요 공지 첨부파일 | `notice/important/{noticeId}/{fileId}` | 장기 보관 대상으로 관리, 필요 시 Glacier 계열 전환 |
| AI 업로드 원본 | `ai/uploads/{jobId}/{fileId}` | 7~30일 후 자동 삭제 |
| AI 중간 결과/로그 | `ai/tmp/{jobId}` | 저장하지 않거나 짧은 기간 후 삭제 |
| RDS snapshot export | `archive/rds-export/{snapshotId}` | S3에 export 후 장기 저비용 보관으로 전환 |

발표에서는 아래처럼 설명한다.

```text
RDS에는 파일 자체를 넣지 않고 파일 ID, 소유 도메인, 상태, 보존기한만 둡니다.
실제 첨부파일과 AI 원본은 S3에 저장하고, 파일 성격에 따라 Lifecycle 정책을 다르게 적용합니다.
결재 첨부파일은 증빙성이 있으므로 장기 보관 대상으로 두고,
AI 업로드 원본처럼 개인정보 위험이 큰 파일은 플랜과 무관하게 짧은 기간 후 자동 삭제합니다.
```

## 도메인별 정책

### 공지사항

공지사항은 삭제 요청 후 바로 완전 삭제하기보다 일정 기간 일반 조회에서 숨긴 뒤 정리하는 데이터다. 화면에 별도 휴지통을 만들지 않더라도, 백엔드에서 삭제 유예 기간을 두면 실수 삭제와 첨부파일 정리를 더 안전하게 처리할 수 있다.

```text
ACTIVE -> DELETED -> HARD_DELETED
```

현재 notice 모듈은 삭제 시 `deleted_at`, `retention_until`을 저장하고, 목록/상세 조회에서는 `deleted_at is null`인 공지만 반환한다. 매일 실행되는 retention 배치가 기간이 지난 공지의 읽음 기록, 첨부 연결, 공지 본문을 순서대로 정리하고, 정리된 `fileId`는 파일 모듈로 넘겨 다른 도메인에서 참조하지 않을 때만 S3 객체와 `file_metadata`를 삭제한다.

### 전자결재

전자결재 문서, 승인/반려 이력, 결재선, 결재 첨부파일은 업무 증빙 데이터로 본다. 플랜에 따라 보관 여부를 다르게 두지 않는다.

```text
DRAFT -> IN_PROGRESS -> APPROVED/REJECTED/CANCELED -> ARCHIVED
```

중요 증빙이나 분쟁 가능 문서는 `legal_hold=true`로 자동 삭제에서 제외한다. "평생 보관"이라고 고정해서 말하기보다, 법적·업무상 보존 필요가 유지되는 동안 자동 삭제하지 않는 구조로 설명한다.

결재 첨부파일의 AI 최종 요약이나 추출 결과가 결재 문서에 반영되면 결재 문서의 일부로 보고 같은 보존 정책을 따른다. 반대로 AI 원본 파일, 프롬프트/응답 원문, 중간 로그, 단순 미리보기 결과는 결재 증빙으로 확정된 데이터가 아니므로 짧게 삭제하거나 저장하지 않는다.

### 학생관리

학생 개인정보는 플랜 혜택으로 장기 보관을 약속하지 않는다. 재원 중에는 운영에 필요한 정보로 보관하고, 퇴원 또는 삭제 이후에는 목적 달성 여부를 기준으로 삭제 또는 익명화한다.

```text
ACTIVE -> WITHDRAWN/DELETED -> ANONYMIZED or HARD_DELETED
```

현재 student 모듈은 삭제 시 `deleted_at`을 채우고, 30일이 지나면 공통 retention 배치가 학생과 수강 이력을 하드 삭제한다. 후속 정책이 필요하면 하드 삭제 대신 이름, 전화번호, 보호자 연락처 같은 식별 필드를 먼저 익명화하는 방식으로 확장한다.

### 강의관리

종료되었거나 삭제된 강의는 유료 플랜에서만 볼 수 있는 혜택으로 두지 않는다. 강의는 수강 이력, 출결, 상담, 매출 판단의 기준이 되므로 운영 이력으로 보관한다.

```text
ACTIVE -> ENDED -> ARCHIVED
ACTIVE -> DELETED
```

현재 lecture 모듈은 삭제 시 `deleted_at`을 채우는 소프트 삭제를 사용하고, 목록/상세 조회와 시간 충돌 검사에서 제외한다. 강의 데이터는 S3 파일을 만들지 않는 RDS 중심 데이터이며, 마감 범위에서는 오래된 강의를 자동 하드 삭제하지 않는다. 후속 구현에서는 종료 강의와 삭제 강의를 일반 운영 화면에서 분리하되, 이력 정합성에 필요한 참조는 유지한다.

### 출결관리

출결은 학생·학부모 응대와 운영 증빙에 필요한 기록이다. 플랜별로 과거 출결 조회 권리를 나누기보다 기본 기록으로 보관하고, 플랜 차등은 SMS 발송량, 엑셀 다운로드, 리포트 같은 사용량·편의 기능에 둔다.

```text
RECORDED -> CORRECTED -> ARCHIVED
```

현재 rollcall 모듈은 강의, 학생, 날짜 단위의 출결 기록과 출결 상태별 문자 템플릿을 RDS에 저장한다. S3에 저장되는 파일은 없다. 출결 문자 발송은 성공 건수만 `resource_usage_event`에 `SMS` 사용량으로 기록하고, 개별 문자 본문·학부모 연락처·발송 원문을 별도 이력 테이블로 장기 저장하지 않는다. 출결 엑셀은 요청 시점에 byte 응답으로 생성하며 DB나 S3에 파일로 남기지 않는다.

## 적용 범위와 이번 문서의 경계

이번 문서는 프론트 화면 추가나 대규모 DB 변경을 요구하지 않는다.

적용 범위:

- notice
- approval
- student
- lecture
- rollcall

적용하지 않는 범위:

- 위 목록 밖의 다른 팀원 도메인
- 실제 인프라 S3 Lifecycle rule 생성
- 전사 개인정보 처리방침 확정
- 법무 검토가 필요한 최종 보존기간 확정

현재 구현되어 있는 내용:

- 학생 삭제 후 30일 retention 배치
- 공지 삭제 시 숨김 처리와 삭제 유예 기간 저장
- 공지 삭제 유예 만료 후 읽음 기록, 첨부 연결, 본문 정리
- 강의 삭제 소프트 삭제
- AI 토큰 사용량 DB 기록
- SMS 발송 성공 건수 DB 기록
- 첨부파일을 file metadata와 S3 객체로 분리 저장

아직 설계 기준으로만 둔 내용:

- 전자결재 장기 아카이브 배치와 운영 화면
- 출결 장기 아카이브 상태
- S3 Lifecycle rule의 실제 인프라 적용
- 학원 계정 프로필 화면의 잔여 사용량/추이 표시

## 발표용 요약

저희는 데이터를 무조건 오래 저장하는 방식이 아니라, 데이터 성격에 따라 생명주기를 나누는 구조로 설계했습니다. 전자결재, 출결, 강의 이력처럼 업무 증빙과 운영 정합성에 필요한 데이터는 플랜과 무관하게 필요한 기간 보관하고, 학생 개인정보나 AI 임시 데이터처럼 민감한 데이터는 목적이 끝나면 삭제 또는 마스킹합니다. RDS는 상태와 보존기한을 관리하고, S3는 파일의 실제 저장 계층과 삭제 시점을 관리합니다. 플랜 차등은 보관기간보다 첨부파일 용량, SMS 발송량, AI 토큰처럼 실제 비용과 연결되는 자원 사용량 중심으로 설계했습니다.

## 2026-08-14 전자결재 보존 정책 적용

전자결재는 학원 운영 과정에서 발생한 내부 승인 증빙이므로, 문서 유형별로 보존 근거를 다르게 둔다. 이번 구현은 문서를 즉시 삭제하지 않고 `approval_document`에 보존 정책을 기록하는 단계다.

| 문서 유형 | 보존 정책 | 기본 보존기한 | 적용 이유 |
| --- | --- | --- | --- |
| 일반 업무 결재, 휴가/근태 관련 결재 | `GENERAL_BUSINESS` | 생성일로부터 3년 | 휴가 등 근로계약 관련 중요 서류는 3년 보존 기준을 따른다. 학원 내부 업무 결재도 분쟁 대응과 운영 확인에 1년은 짧고, 3년이면 일반적인 업무 확인 범위를 커버할 수 있다. |
| 법인카드/비용정산 결재 | `TAX_EVIDENCE` | 생성일로부터 5년 | 장부와 증빙서류는 세무 확인을 위해 5년 보존 기준을 따른다. 영수증 파일과 AI 요약도 해당 결재의 증빙 일부로 보아 같은 정책을 따른다. |
| 계약, 큰 지출, 운영 핵심 의사결정 | `IMPORTANT_BUSINESS` | 생성일로부터 10년 | 상업장부와 영업에 관한 중요서류는 10년 보존 기준을 참고한다. 현재 자동 분류 대상은 아니며, 추후 계약/중요 지출 유형이 생기면 이 정책으로 연결한다. |

적용 컬럼:

| 컬럼 | 의미 |
| --- | --- |
| `retention_policy` | 문서의 보존 정책. 현재 일반 결재는 `GENERAL_BUSINESS`, 법인카드 정산은 `TAX_EVIDENCE`로 자동 지정한다. |
| `retention_until` | 자동 정리나 아카이브 판단에 사용할 보존 만료 기준 시각. |
| `legal_hold` | 분쟁, 감사, 고객 요청 등으로 자동 정리에서 제외해야 할 때 사용하는 보류 플래그. |
| `archived_at` | 일반 조회 영역에서 분리해 장기 보관 상태로 전환한 시각. 이번 구현에서는 컬럼만 준비하고 실제 아카이브 배치는 추후 구현한다. |

운영 원칙:

- 보존기한이 지났다고 즉시 삭제하지 않는다. 먼저 `legal_hold=false`인지 확인하고, 일반 화면에서 분리하는 아카이브 단계를 거친다.
- `approval_history_hidden`은 사용자가 자기 결재 이력에서 숨긴 기록일 뿐 원문 삭제가 아니다. 원문 문서가 존재하는 동안만 의미가 있다.
- `approval_attachment.ai_summary`, `summary_status`, `summarized_at`은 결재 문서에 반영된 결과이므로 원문 결재 문서와 같은 보존 정책을 따른다.
- Gemini 프롬프트/응답 원문, 임시 분석 파일, 단순 미리보기 결과는 결재 증빙으로 확정된 데이터가 아니므로 운영 저장 대상에서 제외하거나 짧게 보관한다.

근거:

- 상법 제33조: 상업장부와 영업에 관한 중요서류 10년, 전표 또는 유사 서류 5년 보존.
- 국세기본법 제85조의3: 장부 및 증빙서류 5년 보존.
- 근로기준법 제42조 및 시행령 제22조: 근로자 명부와 근로계약 관련 중요 서류 3년 보존. 시행령에는 휴가에 관한 서류가 포함된다.
- 개인정보 보호법 제21조: 보유기간 경과나 처리 목적 달성 시 파기하되, 다른 법령에 따른 보존 대상은 분리 보관한다.
