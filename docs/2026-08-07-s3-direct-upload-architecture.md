# S3 직접 업로드 아키텍처 결정

> 작성일: 2026-08-07
> 결정: Finance/Staff 버킷 업로드는 백엔드 서버를 거치지 않고 프론트가 S3에 직접 업로드한다.
> 백엔드는 파일을 받지 않고, 경로(Key)와 업로드 권한(presigned URL)만 발급한다.

## 흐름

1. 프론트 → 백엔드: 업로드 요청
2. 백엔드 → 프론트: presigned URL 발급 (경로 서버 강제 생성 / 업로드 조건 서명 / 짧은 만료)
3. 프론트 → S3: PUT으로 직접 업로드 (백엔드 서버 우회)

## 왜 이 방식인가

- **효율**: 대용량 파일이 백엔드 대역폭·메모리를 안 거쳐서 서버 부하 없고 업로드도 빠름
- **대가**: presigned URL의 "경로"는 브라우저 네트워크 탭에 그대로 보임. 서명(권한)은 만료시간이 짧아 위험 범위가 좁지만, 경로 설계·로그 처리를 잘못하면 이 좁은 위험이 실제 유출로 이어질 수 있음

## 역할 분담

### 백엔드

- presigned URL 발급 시 경로(Key)를 서버가 직접 생성한다 (프론트가 보낸 경로를 신뢰하지 않는다)
- 경로에 실명·주민번호 등 PII를 넣지 않고 UUID 등 opaque ID로 구성한다. 실제 파일명·소유자 매핑은 RDS에서 관리한다
- 만료시간을 짧게 설정한다 (수 분)
- Content-Type·파일 크기 상한을 서명 조건에 포함한다
- 업로드 완료 후 S3 HEAD 확인 또는 이벤트 알림 기반으로 RDS 정합성을 반영한다 (클라이언트 완료 콜백만 신뢰하지 않는다)

### 프론트

- 백엔드가 내려준 URL을 그대로, 변형 없이 사용한다 (경로 직접 생성·편집 금지)
- 업로드 시 서명 조건과 일치하는 헤더(Content-Type 등)로 요청한다 (안 맞으면 S3가 403 반환)
- URL을 콘솔 로그·에러 트래킹 툴·외부 공유 링크에 그대로 남기지 않는다

### 인프라

- 버킷 Public access 차단 상태를 유지한다 (경로를 알아도 서명 없이는 접근 불가능해야 한다)
