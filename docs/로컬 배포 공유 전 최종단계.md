# 로컬 배포 공유 전 최종단계

이 문서는 `develop`의 최신 애플리케이션 코드를 `infra` 브랜치에 병합한 뒤, 로컬 Docker 배포 환경을 팀원에게 공유하기 전에 수행할 최종 작업을 정리한다.

## 목표

다음 상태를 모두 만족하면 로컬 배포 환경을 팀원에게 공유할 수 있다.

- MySQL과 Spring Boot 애플리케이션이 Docker Compose로 함께 실행된다.
- 애플리케이션 이미지를 현재 소스로 다시 빌드할 수 있다.
- 애플리케이션 헬스체크가 `UP`을 반환한다.
- Flyway 마이그레이션이 정상 적용된다.
- 컨테이너를 재시작해도 DB 데이터가 유지된다.
- 개인 비밀번호와 JWT 시크릿이 Git에 포함되지 않는다.
- 다른 팀원이 저장소와 Docker Desktop만으로 같은 환경을 재현할 수 있다.

## 현재 로컬 Docker 구성

| 항목 | 설정 |
|---|---|
| 애플리케이션 호스트 주소 | `http://localhost:8080` |
| 헬스체크 | `http://localhost:8080/actuator/health` |
| MySQL 호스트 주소 | `localhost:3307` |
| 컨테이너 내부 MySQL 주소 | `mysql:3306` |
| 데이터베이스 | `mudo_groupware` |
| Docker 이미지 | `mudo-groupware-backend:local` |
| Compose 프로젝트 | `mudo-groupware-local` |
| DB 데이터 볼륨 | `mudo-groupware-local_mudo-mysql-data` |

호스트의 `3306`은 로컬에 설치된 MySQL이 사용할 수 있으므로 Docker MySQL은 기본적으로 `3307`에 연결한다. 애플리케이션 컨테이너는 호스트 포트가 아니라 Docker 네트워크의 `mysql:3306`으로 접속한다.

## 1. 병합 전 작업 트리 확인

`infra` 브랜치인지 확인한다.

```powershell
git branch --show-current
git status --short
```

기존 작업을 잃지 않도록 현재 변경 파일과 미추적 파일을 먼저 확인한다. 특히 다음 Docker 설정 파일은 병합 과정에서 삭제하지 않는다.

```text
Dockerfile
docker-compose.local.yml
.dockerignore
.env.local
.gitignore
```

`.env.local`에는 팀 공용 로컬 개발 값만 두고 Git에 포함한다. 운영 비밀번호나 운영 JWT 시크릿은 절대 넣지 않는다.

## 2. `develop` 코드 병합 및 충돌 해결

원격 상태를 갱신한 뒤 `develop`을 병합한다.

```powershell
git fetch origin
git merge origin/develop
```

충돌이 발생하면 다음 기준으로 해결한다.

- Java 애플리케이션 코드와 `build.gradle`은 최신 `develop` 구현을 우선한다.
- Docker 관련 파일은 `infra` 브랜치에서 만든 설정을 유지한다.
- `application.yaml`과 `application-local.yaml`이 변경됐다면 Compose의 `SPRING_DATASOURCE_*` 환경변수가 최종적으로 우선 적용되는지 확인한다.
- Java 버전, Gradle 버전 또는 JAR 생성 방식이 변경됐다면 `Dockerfile`도 함께 수정한다.
- DB 엔진 버전이 변경됐다면 `docker-compose.local.yml`의 `mysql:8.0` 이미지가 여전히 맞는지 확인한다.

충돌 해결 후 남은 충돌 표시가 없는지 확인한다.

```powershell
rg -n "^(<<<<<<<|=======|>>>>>>>)" .
git status --short
```

## 3. Docker 밖에서 애플리케이션 검증

Docker 문제와 애플리케이션 문제를 구분하기 위해 먼저 Gradle 검증을 수행한다.

```powershell
.\gradlew.bat clean test --no-daemon
.\gradlew.bat bootJar --no-daemon
```

두 명령이 모두 `BUILD SUCCESSFUL`로 끝나야 한다. 실패하면 Docker 설정을 수정하기 전에 애플리케이션 컴파일, 테스트 또는 의존성 문제부터 해결한다.

## 4. 공용 로컬 환경변수 확인

저장소에서 받은 `.env.local`에 다음 공용 로컬 값이 있는지 확인한다.

```dotenv
LOCAL_MYSQL_ROOT_PASSWORD=local-root-password-2026
DB_USERNAME=mudo_app
DB_PASSWORD=local-db-password-2026
JWT_SECRET=<저장소에 등록된 로컬 연동 테스트 전용 값>
MYSQL_HOST_PORT=3307
APP_HOST_PORT=8080
```

실제 값이 Git에 잡히지 않는지 확인한다.

```powershell
git check-ignore -v .env.local
git status --short
```

`git status`에 `.env.local`이 나타나면 공유하기 전에 반드시 `.gitignore`를 수정한다.

## 5. 포트 충돌 확인

```powershell
Get-NetTCPConnection -State Listen -ErrorAction SilentlyContinue |
  Where-Object LocalPort -In 3307, 8080 |
  Select-Object LocalAddress, LocalPort, OwningProcess
```

포트가 이미 사용 중이면 기존 프로세스를 무조건 종료하지 말고 `.env.local`의 `MYSQL_HOST_PORT` 또는 `APP_HOST_PORT`를 다른 값으로 변경한다.

## 6. Compose 설정 검증

```powershell
docker compose --env-file .env.local -f docker-compose.local.yml config --quiet
docker compose --env-file .env.local -f docker-compose.local.yml config --services
```

첫 번째 명령은 오류 없이 끝나야 하고, 두 번째 명령에는 다음 두 서비스만 표시돼야 한다.

```text
mysql
app
```

## 7. 최신 코드로 이미지 빌드 및 실행

이전에 만든 이미지가 있더라도 병합한 코드를 반영하기 위해 반드시 `--build`를 사용한다.

```powershell
docker compose --env-file .env.local -f docker-compose.local.yml up -d --build
```

상태를 확인한다.

```powershell
docker compose --env-file .env.local -f docker-compose.local.yml ps
```

MySQL과 앱이 모두 `running` 상태이고 잠시 후 `healthy`가 되어야 한다.

실패하면 로그를 확인한다.

```powershell
docker compose --env-file .env.local -f docker-compose.local.yml logs --tail 200 mysql
docker compose --env-file .env.local -f docker-compose.local.yml logs --tail 200 app
```

## 8. 애플리케이션 헬스체크

```powershell
Invoke-RestMethod http://localhost:8080/actuator/health
```

예상 결과:

```text
status : UP
```

`APP_HOST_PORT`를 변경했다면 URL의 `8080`도 해당 포트로 변경한다.

### IntelliJ에서 애플리케이션을 직접 실행할 때

Docker의 `app` 서비스와 IntelliJ 애플리케이션은 기본적으로 모두 호스트의 `8080` 포트를 사용하므로 동시에 실행할 수 없다. IntelliJ로 실행할 때는 MySQL은 유지하고 Docker 앱만 중지한다.

```powershell
docker compose --env-file .env.local -f docker-compose.local.yml stop app
```

IntelliJ에서 Docker MySQL을 사용할 경우 datasource 주소는 `localhost:3307`이고 계정은 `.env.local`의 `DB_USERNAME`, `DB_PASSWORD`와 같아야 한다. `application-local.yaml`의 기본 주소인 `localhost:3306`은 PC에 직접 설치한 MySQL을 사용할 때의 주소다.

Docker 로컬 배포로 돌아갈 때는 앱 서비스를 다시 실행한다.

```powershell
docker compose --env-file .env.local -f docker-compose.local.yml up -d app
```

## 9. Flyway 및 DB 스키마 확인

다음 명령의 비밀번호는 `.env.local`의 `DB_PASSWORD` 값으로 바꾼다.

```powershell
docker compose --env-file .env.local -f docker-compose.local.yml exec -T `
  -e MYSQL_PWD=<DB_PASSWORD> mysql `
  mysql -u mudo_app -D mudo_groupware `
  -e "SHOW TABLES; SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;"
```

확인할 내용:

- 애플리케이션이 사용하는 테이블이 생성돼 있다.
- `flyway_schema_history`가 존재한다.
- 모든 마이그레이션 행의 `success` 값이 `1`이다.

`flyway_schema_history`가 없다면 Docker나 MySQL 생성 문제가 아니라 애플리케이션의 Flyway 의존성·자동설정·마이그레이션 경로 문제일 가능성이 높다. 이 경우 `develop` 코드에서 Flyway 설정을 확인한다.

## 10. 재시작 검증

앱만 재시작한다.

```powershell
docker compose --env-file .env.local -f docker-compose.local.yml restart app
docker compose --env-file .env.local -f docker-compose.local.yml logs --tail 100 app
Invoke-RestMethod http://localhost:8080/actuator/health
```

재시작 후에도 헬스체크가 `UP`이어야 한다.

## 11. DB 데이터 유지 검증

Compose 서비스를 내리되 볼륨은 삭제하지 않는다.

```powershell
docker compose --env-file .env.local -f docker-compose.local.yml down
docker compose --env-file .env.local -f docker-compose.local.yml up -d
```

다시 헬스체크하고 DB 테이블이 유지되는지 확인한다.

```powershell
Invoke-RestMethod http://localhost:8080/actuator/health
```

`down`은 컨테이너와 네트워크만 제거하고 DB 볼륨은 유지한다.

다음 명령은 DB 볼륨까지 삭제하므로 초기화가 확실히 필요한 경우에만 사용한다.

```powershell
docker compose --env-file .env.local -f docker-compose.local.yml down -v
```

## 12. 팀 공유 전 Git 확인

```powershell
git status --short
git diff --check
git diff -- Dockerfile docker-compose.local.yml .dockerignore .env.local .gitignore
```

확인할 내용:

- `.env.local`에는 공개 가능한 로컬 개발 값만 있다.
- 운영 비밀번호, 운영 JWT 시크릿, AWS 키가 포함되지 않았다.
- `logs/`, `build/`, `.gradle/` 같은 로컬 산출물이 포함되지 않았다.
- 애플리케이션 코드 변경은 의도한 `develop` 병합 결과만 존재한다.
- Docker 설정에 특정 팀원의 절대 경로가 없다.

## 13. 팀원에게 공유할 실행 방법

팀원에게는 다음 절차만 안내하면 된다.

```powershell
git pull
docker compose --env-file .env.local -f docker-compose.local.yml up -d --build
Invoke-RestMethod http://localhost:8080/actuator/health
```

일상적인 사용 명령:

```powershell
# 상태 확인
docker compose --env-file .env.local -f docker-compose.local.yml ps

# 로그 확인
docker compose --env-file .env.local -f docker-compose.local.yml logs -f app

# 코드 변경 후 이미지 재빌드
docker compose --env-file .env.local -f docker-compose.local.yml up -d --build app

# 종료, DB 데이터 유지
docker compose --env-file .env.local -f docker-compose.local.yml down
```

## 최종 공유 체크리스트

- [ ] `develop` 최신 코드 병합 및 충돌 해결 완료
- [ ] Gradle 테스트 및 `bootJar` 성공
- [ ] `.env.local`에 공용 로컬 값만 존재하고 Git에 포함됐는지 확인
- [ ] Compose 문법 검증 성공
- [ ] MySQL 및 앱 컨테이너 정상 기동
- [ ] 애플리케이션 헬스체크 `UP`
- [ ] Flyway 및 업무 테이블 생성 확인
- [ ] 앱 재시작 후 정상 동작 확인
- [ ] Compose 재기동 후 DB 데이터 유지 확인
- [ ] 운영 비밀값과 로컬 산출물이 커밋 대상에 없는지 확인
- [ ] 다른 PC에서 동일 절차로 1회 재현 확인

위 항목을 모두 통과한 후 로컬 Docker 설정을 `develop`에 반영하고 팀원에게 공유한다. `main` 머지에 따른 운영 CD 구성은 이 로컬 배포 검증이 끝난 다음 별도 단계로 진행한다.
