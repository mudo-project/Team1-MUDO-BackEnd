# 🧪 더미 데이터 설정 가이드

개발·Postman 테스트에 필요한 더미 데이터는 **최신 DB 덤프를 먼저 확인한 뒤** 생성합니다.
스키마, FK, enum 값, 기존 데이터가 마이그레이션마다 달라질 수 있으므로 이전 SQL을 그대로 재사용하지 않습니다.

---

## 1. 운영 원칙

- ✅ 새 마이그레이션 반영 후에는 최신 DB 덤프를 기준으로 더미 SQL을 다시 작성합니다.
- ✅ 더미 데이터는 개발자가 MySQL Workbench 등에서 직접 실행합니다.
- ✅ Codex 또는 Claude Code는 덤프를 확인해 실행용 SQL과 Postman 기대 결과를 채팅으로 제공합니다.
- ❌ Flyway 마이그레이션 파일에 테스트용 더미 데이터를 넣지 않습니다.
- ❌ Codex·Claude Code가 별도 확인 없이 실제 DB·덤프 파일에 자동으로 INSERT 하지 않습니다.

---

## 2. 더미 데이터 요청 방법

새 더미 데이터가 필요하면 최신 덤프 폴더의 **절대 경로**와 아래 정보를 채팅으로 전달합니다.

```text
[더미 데이터 요청]
덤프 경로: C:\...\DumpYYYYMMDD
대상 계정: user01@test.com (userId=1)
대상 기능: (예) 워크스페이스 업무 상세 조회
필요 건수: (예) 진행 중 업무 5건
검증 API: (예) GET /api/workspaces/{workspaceId}/tasks/{taskId}
```

덤프 경로만 전달해도 스키마를 먼저 확인할 수 있지만, 대상 계정·기능·건수를 함께 주면 더 정확한 SQL을 만들 수 있습니다. 🙌

---

## 3. 확인 절차

```text
최신 DB 덤프 경로 전달
→ 대상 테이블 DDL 확인
→ 관련 사용자·대상 엔티티의 실제 ID 및 기존 데이터 확인
→ NOT NULL / FK / enum / 기본값 확인
→ 중복·기존 데이터 반영
→ 실행용 INSERT SQL과 검증 SELECT 제공
→ 개발자가 로컬 DB에 직접 실행
→ Postman으로 API 응답 확인
```

### 확인 항목

| 항목 | 확인 이유 |
| --- | --- |
| 테이블 컬럼·타입 | 마이그레이션으로 추가·삭제된 컬럼 누락 방지 |
| NOT NULL·기본값 | INSERT 실패 방지 |
| 외래키 | 존재하지 않는 사용자·대상 ID 참조 방지 |
| enum 값 | 애플리케이션 역직렬화 오류 방지 |
| 기존 데이터 | 기대 건수와 실제 API 응답 차이 방지 |

---

## 4. 더미 데이터 작성 기준 (범용)

요청받은 대상 테이블·API마다 컬럼 구성이 다르므로, 아래 순서로 확인한 뒤 값을 채웁니다.

```text
대상 테이블 DDL 확인 (덤프 기준)
→ 대상 API가 실제로 사용하는 조회 조건 확인 (컨트롤러/쿼리 코드 또는 API 문서)
→ 그 조회 조건에 해당하는 컬럼부터 우선 채움
→ 나머지 NOT NULL·FK·enum 컬럼 채움
```

| 항목 | 채우는 기준 |
| --- | --- |
| PK / FK | 덤프에 실제로 존재하는 사용자·연관 엔티티 ID를 참조합니다. 존재하지 않는 ID를 임의로 만들지 않습니다. |
| 조회 조건 컬럼 | 대상 API가 WHERE·필터로 실제 사용하는 컬럼(상태값, 소프트 삭제 컬럼, 만료 시각 등)입니다. 대상 API의 코드나 API 문서를 확인해 값을 정확히 맞춥니다 — 이게 틀리면 더미 데이터를 넣어도 API 응답에 안 잡힙니다. |
| NOT NULL / 기본값 | 덤프의 DDL 기준으로 채웁니다. 마이그레이션으로 추가·삭제된 컬럼이 있을 수 있으므로 이전에 썼던 INSERT문을 재사용하지 않습니다. |
| enum 값 | 덤프 시점에 애플리케이션이 실제로 쓰는 유효한 enum 값입니다. 코드의 enum 정의와 대조합니다. |
| 소프트 삭제 컬럼(`deleted_at` 등) | 존재하는 레코드로 취급하려면 `NULL`로 둡니다. |
| 대상 참조 컬럼(예: `target_type`/`target_id`류) | 수신자·소유자 ID가 아니라, 클릭·이동 시 참조하는 **다른 도메인의 실제 엔티티 ID**인 경우가 많습니다. 컬럼명만 보고 넘겨짚지 않고 실제 용도를 확인합니다. |

> 💡 이 표는 매번 어떤 컬럼이 있는지를 정의하는 게 아니라 "어떤 순서로, 무엇을 먼저 확인해야 하는지"를 정의합니다. 실제 컬럼 목록은 요청 시점 덤프에서 매번 다시 확인합니다.

## 5. 검증 기준 (범용)

더미 SQL 실행 전후로, **대상 API가 실제로 사용하는 조회 조건과 동일한 SELECT**를 먼저 실행해 기대값을 확인합니다.

```text
대상 API의 조회 조건 확인 (컨트롤러/서비스 코드 또는 API 문서)
→ 그 조건과 동일한 SELECT/COUNT 쿼리 작성
→ 더미 SQL 실행 전후로 각각 실행해 기대값 확정
→ 대상 계정의 Access Token으로 대상 API 호출
→ API 응답 필드와 SELECT 결과를 비교
```

예시 형태(실제 쿼리·API는 요청 시점 대상에 맞춰 매번 다시 작성):

```text
GET {대상 API 경로}
Authorization: Bearer {accessToken}
```

응답의 대상 필드 값은 위에서 확인한 SELECT 결과와 같아야 합니다.

---

## 6. 마이그레이션 이후 갱신 규칙

마이그레이션으로 테이블·제약 조건·enum·대상 도메인 구조가 변경되면 다음 순서로 진행합니다.

```text
마이그레이션 적용
→ 최신 DB 덤프 생성
→ 새 덤프 경로를 Codex·Claude Code 채팅에 전달
→ 더미 데이터 SQL 재검토·재작성
→ 검증 SQL과 Postman 기대값 갱신
```

이 문서는 요청 절차와 검증 기준을 유지합니다. 실제 INSERT SQL은 **덤프 확인 시점의 최신 구조**를 기준으로 채팅에서 제공합니다.
