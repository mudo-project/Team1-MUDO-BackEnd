# DATABASE.md

## 시간대 정책

- 서버 JVM 기본 시간대는 UTC로 사용한다.
- 데이터베이스 연결 세션 시간대는 `Asia/Seoul`로 설정한다.
- 데이터베이스에 저장하는 날짜·시간의 기준은 `Asia/Seoul (UTC+09:00)`이다.
- 날짜·시간 생성·변환 시 시스템 기본 시간대에 의존하지 않고, `Asia/Seoul` 또는 UTC를 명시적으로 사용한다.
- API 응답은 `Asia/Seoul` 기준의 ISO-8601 오프셋 형식으로 반환한다.
- 생성일·수정일·삭제일 컬럼을 갖는 JPA Entity의 상속 규칙은 [ARCHITECTURE.md](ARCHITECTURE.md)의 "Domain Model과 JPA Entity" 섹션을 따른다.

## Flyway 마이그레이션

- Flyway는 `out-of-order: true`로 실행한다. 이 설정은 "담당자별로 병렬 작업하다 늦게 병합되는 마이그레이션이 이미 적용된 최대 버전보다 낮은 버전일 수 있는 상황"을 위한 것이다. **테이블 생성보다 그 테이블을 참조하는 마이그레이션이 낮은 버전으로 먼저 실행되는 의존성 순서 역전까지 해결해주지는 않는다** — 이 경우 기존 dev/운영 DB는 시간순으로 우연히 통과하지만, 신규(빈) DB에서 처음부터 전체를 실행하면 실패한다(2026-08-06 `V1.4.3`/`V1.4.6`/`V2.1.8`이 `V4.1.2`의 `permission` 테이블보다 먼저 실행되어 실제로 발생).
- 마이그레이션 파일은 `src/main/resources/db/migration/be{담당자번호}/` 경로에 생성한다.
- 파일명은 `V{담당자번호}.{묶음번호}.{순번}__{설명}.sql` 형식을 사용한다.
- 담당자번호는 팀원별로 할당된 번호를 사용한다.
- 같은 담당자번호와 묶음번호 안에서는 순번을 `1`부터 `9`까지 사용한다. 순번이 `9`에 도달하면 묶음번호를 증가시키고 순번을 `1`부터 다시 시작한다.
- 예: `V1.1.1__create_users_table.sql`부터 `V1.1.9__...sql`까지 사용한 다음 파일은 `V1.2.1__...sql`로 생성한다.
- 늦게 병합되는 마이그레이션은 이미 적용된 최대 버전보다 낮은 버전일 수 있으며, Flyway가 Out-of-Order로 적용한다.
- 이미 배포된 마이그레이션 파일은 수정하거나 삭제하지 않는다.
  - **예외**: 위와 같은 구조적 순서 역전 문제를 근본적으로 없애기 위해 팀 합의로 기존 마이그레이션 전체를 하나의 베이스라인으로 스쿼시하는 경우에 한해 예외를 허용한다. 이 경우 원본 파일은 삭제하지 않고 `src/main/resources/db/migration-archive/`(Flyway가 스캔하지 않는 경로)로 이동해 그대로 보존하며, 기존에 이미 마이그레이션이 적용된 dev/운영 DB는 파일 내용 대신 `flyway baseline`으로 "베이스라인 버전까지는 이미 적용됨"만 마킹하고 재실행하지 않는다. 2026-08-06에 `db/migration/baseline/V0__baseline_consolidated_schema.sql` 1건으로 처음이자 유일하게 이 예외를 적용했고, 이후 담당자별 버전은 다시 `1`부터 새로 부여한다.
- 신규 마이그레이션은 이전 마이그레이션의 적용 결과에 의존하는 순서를 명확히 정의하고, 운영 환경 적용 전 `validate`로 이력과 파일 무결성을 검증한다. 참조하는 테이블/컬럼이 다른 담당자 폴더의 마이그레이션에서 먼저 생성되는지 반드시 확인한다.
- CI는 완전히 빈 스키마에서 전체 마이그레이션이 순서대로 성공하는지 검증하는 테스트(`FlywayFreshDatabaseMigrationTest`, Testcontainers)를 포함한다. 새 마이그레이션이 이 검증을 통과하지 못하면 머지할 수 없다. **담당자별 버전 번호를 계속 쓰는 한 이 CI 게이트가 실질적인 유일한 안전장치다** — 번호 방식 자체는 순서 역전을 구조적으로 막아주지 않는다.

### 충돌 발생 시 대응

CI의 `FlywayFreshDatabaseMigrationTest`가 실패하면(빈 DB에서 전체 마이그레이션 중 일부가 실패) 다음 순서로 해결한다.

1. CI 로그에서 실패한 마이그레이션의 버전과 SQL 에러(주로 "테이블/컬럼이 존재하지 않음")를 확인한다.
2. 그 마이그레이션이 참조하는 테이블/컬럼을 실제로 생성하는 마이그레이션 파일을 찾는다.
3. 참조하는 쪽의 버전(묶음번호.순번)이 생성하는 쪽보다 낮다면, 참조하는 쪽의 버전을 생성하는 쪽보다 높게 재조정한다(같은 PR 안의 파일이면 바로 조정 가능하고, 이미 develop에 머지된 다른 담당자의 파일을 참조한다면 그 파일의 버전보다 높은 다음 순번을 받는다).
4. 로컬에서 빈 MySQL(Testcontainers 또는 throwaway 컨테이너)에 재현해 확인 후 다시 push한다.
5. 여러 파일이 서로 얽혀 손으로 순서를 맞추기 어려우면, 실제 Flyway로 스크래치 환경에 돌려 올바른 순서를 찾고 검증하는 방식(2026-08-06 베이스라인 통합 때 사용한 방식)을 축소해 적용한다.
