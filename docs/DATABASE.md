# DATABASE.md

## 시간대 정책

- 서버 JVM 기본 시간대는 UTC로 사용한다.
- 데이터베이스 연결 세션 시간대는 `Asia/Seoul`로 설정한다.
- 데이터베이스에 저장하는 날짜·시간의 기준은 `Asia/Seoul (UTC+09:00)`이다.
- 날짜·시간 생성·변환 시 시스템 기본 시간대에 의존하지 않고, `Asia/Seoul` 또는 UTC를 명시적으로 사용한다.
- API 응답은 `Asia/Seoul` 기준의 ISO-8601 오프셋 형식으로 반환한다.
- 생성일·수정일·삭제일 컬럼을 갖는 JPA Entity의 상속 규칙은 [ARCHITECTURE.md](ARCHITECTURE.md)의 "Domain Model과 JPA Entity" 섹션을 따른다.

## Flyway 마이그레이션

- Flyway는 `out-of-order: true`로 실행한다. 이 설정은 "담당자별로 병렬 작업하다 늦게 병합되는 마이그레이션이 이미 적용된 최대 버전보다 낮은 버전일 수 있는 상황"을 위한 것이다. **테이블 생성보다 그 테이블을 참조하는 마이그레이션이 낮은 버전으로 먼저 실행되는 의존성 순서 역전까지 해결해주지는 않는다** — 이 경우 기존 dev/운영 DB는 시간순으로 우연히 통과하지만, 신규(빈) DB에서 처음부터 전체를 실행하면 실패한다(2026-08-06 `V1.4.3`/`V1.4.6`/`V2.1.8`이 `V4.1.2`의 `permission` 테이블보다 먼저 실행되어 실제로 발생).
- 신규 마이그레이션 파일은 `src/main/resources/db/migration/be{담당자번호}/` 경로에 생성한다.
- 파일명은 `V{YYYYMMDD}_{HHmm}__{설명}.sql` 형식(타임스탬프 버전)을 사용한다. 예: `V20260807_1400__add_something.sql`. `be{담당자번호}` 폴더 구조는 소유권 표시 용도로 유지하되, Flyway는 폴더가 아니라 파일명의 버전 문자열만 보고 전체를 오름차순으로 실행하므로 폴더가 달라도 버전 역전이 발생하지 않는다.
  - 2026-08-06 이전에는 `V{담당자번호}.{묶음번호}.{순번}__{설명}.sql`(예: `V1.4.3__...sql`) 형식을 사용했다. 이 형식은 폴더별(=담당자별) 버전 앞자리가 실제 작성 시점과 무관해 신규 DB에서 순서 역전을 일으킬 수 있어 타임스탬프 형식으로 전환했다.
- 이미 배포된 마이그레이션 파일은 수정하거나 삭제하지 않는다.
  - **예외**: 위와 같은 구조적 순서 역전 문제를 근본적으로 없애기 위해 팀 합의로 기존 마이그레이션 전체를 하나의 베이스라인으로 스쿼시하는 경우에 한해 예외를 허용한다. 이 경우 원본 파일은 삭제하지 않고 `src/main/resources/db/migration-archive/`(Flyway가 스캔하지 않는 경로)로 이동해 그대로 보존하며, 기존에 이미 마이그레이션이 적용된 dev/운영 DB는 파일 내용 대신 `flyway baseline`으로 "베이스라인 버전까지는 이미 적용됨"만 마킹하고 재실행하지 않는다. 2026-08-06에 `db/migration/baseline/V8.0.0__baseline_consolidated_schema.sql` 1건으로 처음이자 유일하게 이 예외를 적용했다.
- 신규 마이그레이션은 이전 마이그레이션의 적용 결과에 의존하는 순서를 명확히 정의하고, 운영 환경 적용 전 `validate`로 이력과 파일 무결성을 검증한다. 참조하는 테이블/컬럼이 다른 담당자 폴더의 마이그레이션에서 먼저 생성되는지 반드시 확인한다.
- CI는 완전히 빈 스키마에서 전체 마이그레이션이 순서대로 성공하는지 검증하는 테스트(Testcontainers)를 포함한다. 새 마이그레이션이 이 검증을 통과하지 못하면 머지할 수 없다.
