# Workspace 비즈니스 정책

- 최초 작성일: 2026-08-04
- 상태: 정책 확정 / 권한 모듈 연동은 추후 구현

## 🎯 모듈 책임

- 학원 안에서 워크스페이스, 참여자, 업무, 업무 댓글, 반복 업무를 관리한다.
- 사용자·학원·권한의 원본 데이터는 다른 모듈이 소유한다.
- `academy_id`, `user_id`, `created_by` 등 외부 도메인 식별자는 값으로만 보관하며, 직접 JPA 연관관계를 맺지 않는다.

## 🔐 접근 권한

### 일반 참여자

- 현재 `workspace_member`에 존재하는 사용자는 워크스페이스의 업무·댓글을 생성, 조회, 수정, 삭제할 수 있다.
- 참여자는 다른 참여자의 댓글도 수정·삭제하고 완료·완료 취소할 수 있다.
- 참여자 추가·제거는 워크스페이스 생성 권한을 보유하면서 현재 참여자인 사용자만 할 수 있다.
- 일반 참여자는 워크스페이스 생성자를 참여자에서 제거할 수 없다.

### 학원 관리자

- 학원 관리 권한자는 참여 여부와 무관하게 같은 학원의 모든 워크스페이스를 생성, 조회, 수정, 삭제할 수 있다.
- 학원 관리 권한자는 비참여 워크스페이스의 업무·댓글·상태 이력도 조회하고 관리할 수 있다.
- 권한 보유 여부와 학원 소속 여부는 추후 권한 모듈의 공개 계약으로 검증한다.

### 목록 조회 범위

- 워크스페이스 목록의 기본 범위는 현재 사용자가 참여 중인 활성 워크스페이스이다(`scope=MINE`).
- 권한 모듈 연동 후 `WORKSPACE:READ_ALL` 권한자는 같은 학원의 모든 활성 워크스페이스를 조회할 수 있다(`scope=ALL`).
- 상태: 참여 워크스페이스 목록 조회 적용
- `WORKSPACE:READ_ALL` 기반 전체 워크스페이스 조회는 권한 모듈 연동 후 적용 예정
- 다른 학원의 워크스페이스는 권한 종류와 관계없이 조회 대상에서 제외한다.

## 🗂️ 워크스페이스

### 생성과 이름

- 워크스페이스 생성자는 자동으로 참여자로 등록한다.
- 같은 학원에서 활성 상태인 워크스페이스 이름은 고유하다.
- 생성 또는 이름 수정 시 중복 이름이면 자동 변경하지 않고 중복 오류를 반환한다.
- 복사 기능을 구현할 때만 중복 이름에 가장 작은 사용 가능 번호를 붙여 생성한다.
- 이름 앞뒤 공백은 제거한 뒤 중복을 검사한다.
- 이름은 최대 100자이다.

### 삭제와 복구

- 워크스페이스는 소프트 삭제한다. 삭제된 워크스페이스와 하위 업무·댓글·이력은 일반 조회에서 모두 제외한다.
- 삭제 후 30일 동안 복구할 수 있으며, 기간 종료 후 워크스페이스와 하위 데이터를 물리 삭제한다.
- 삭제된 워크스페이스 이름은 즉시 재사용할 수 있다.
- 복구하려는 이름이 이미 활성 워크스페이스에 존재하면, 가장 작은 사용 가능 번호를 붙인 이름으로 복구한다.
- 활성 이름 고유성은 `active_name` 생성 컬럼으로 구현한다.

```text
active_name = CASE WHEN deleted_at IS NULL THEN name ELSE NULL END
UNIQUE (academy_id, active_name)
```

### 목록과 최근 접속

- 목록 응답에는 워크스페이스 식별자, 이름, 현재 참여자 수만 제공한다.
- 목록은 요청한 사용자 기준 최근 접속 시각이 최신인 순서로 정렬한다. 최근 접속 기록이 없으면 워크스페이스 생성 시각이 최신인 순서로 뒤에 배치한다.
- 워크스페이스 상세 화면을 정상적으로 연 뒤 `PUT /api/workspaces/{workspaceId}/recent-access`를 호출해 최근 접속 시각을 기록한다. 목록을 불러온 것만으로는 접속 기록을 갱신하지 않는다.
- 최근 접속 기록은 공유 워크스페이스 상태가 아니라 사용자별 상태이다. 한 사용자가 같은 워크스페이스에 다시 접속하면 기존 행의 시각을 갱신한다.
- `workspace_recent_access`는 `(user_id, workspace_id)`를 복합 PK로 사용하므로 사용자·워크스페이스 조합당 최대 한 행만 저장한다.
- 최근 접속 기록은 MySQL의 `INSERT ... ON DUPLICATE KEY UPDATE`로 저장해, 같은 최초 접속 요청이 동시에 들어와도 중복 키 오류 없이 한 행을 생성하거나 갱신한다. 늦게 도착한 요청의 시각이 더 과거면 기존의 더 최신 접속 시각을 유지한다.
- 삭제된 워크스페이스는 목록과 최근 접속 기록 대상에서 제외한다.

## 👥 참여자

- `workspace_member`는 현재 참여 상태만 표현한다.
- 복합 PK는 `(workspace_id, user_id)`이다.
- 참여자 추가는 행 삽입, 제거는 행 물리 삭제로 처리한다.
- 재참여 이력은 저장하지 않는다.
- 나중에 참여한 사용자도 참여 전의 업무·댓글·상태 이력을 모두 조회할 수 있다.
- 제거된 사용자의 기존 업무·댓글·멘션 기록은 유지하지만 이후 접근과 알림은 허용하지 않는다.

## ✅ 업무

- 업무와 반복 업무 템플릿은 제목만 가지며, 본문은 업무 댓글로만 작성한다.

### 상태와 마감일

- 업무 상태는 `WAITING`, `IN_PROGRESS`, `COMPLETED`, `DELAYED`를 사용한다.
- `due_at`은 nullable이다. 마감일이 없는 업무는 자동 지연 대상이 아니다.
- 자동 지연 조건은 `due_at IS NOT NULL`, `due_at < 현재 시각`, `status != COMPLETED`이다.
- 스케줄러가 자동으로 지연 처리할 때 `task_status_history.changed_by`는 `NULL`로 저장한다. `NULL`은 시스템 처리자를 의미한다.
- 과거 마감일로 미완료 업무를 생성하면 최초 상태를 `DELAYED`로 저장한다.
- 최초 상태 이력은 `previous_status = NULL`로 저장한다.
- 지연 업무를 진행 중으로 바꾸려면 미래의 새 마감일을 함께 입력해야 한다. UI에서는 상태 변경 시 마감일 입력 모달을 제공한다.
- 지연 업무는 마감일 수정 없이 완료 처리할 수 있다.

### 삭제

- 업무는 복구 없이 하드 삭제한다.
- 삭제 전 UI에서 업무와 하위 댓글·멘션·상태 이력이 즉시 삭제되고 복구할 수 없음을 안내한다.
- 업무 삭제 시 댓글, 댓글 멘션, 상태 변경 이력도 함께 삭제한다.

## 💬 업무 댓글과 멘션

- 업무 댓글은 협업 메모이면서 하위 할 일로 사용할 수 있다.
- 댓글 생성 시 `is_completed = false`, `completed_by = NULL`, `completed_at = NULL`이다.
- 완료 처리 시 완료 처리자와 시각을 기록하고, 완료 취소 시 두 값을 다시 `NULL`로 변경한다.
- 이미 완료된 댓글에 대한 완료 재요청과 미완료 댓글에 대한 완료 취소 재요청은 기존 값을 유지하는 멱등 처리로 응답한다.
- 완료 취소 후 다시 완료하면 새 완료 처리자와 시각을 기록한다.
- 완료 시각은 클라이언트 입력값이 아닌 Application Service의 `Clock` 기준으로 결정한다.
- 상위 업무가 완료되어도 댓글을 자동으로 완료하지 않는다.
- `author_id`는 최초 작성자이며 댓글 수정 후에도 변경하지 않는다.
- 화면에는 최초 작성자와 작성일만 표시한다. 마지막 수정자는 기록하지 않는다.
- 멘션 대상은 현재 워크스페이스 참여자만 가능하다.
- 댓글 하나에 같은 사용자를 중복 멘션할 수 없다: `UNIQUE (comment_id, mentioned_user_id)`.
- 멘션된 사용자가 나중에 제거되어도 기존 멘션 기록은 유지하되, 이후 알림과 접근 권한은 주지 않는다.

## 🔁 반복 업무

### 템플릿과 생성

- 반복 업무는 `recurring_task_template`이 관리하고, 스케줄러가 개별 `task`를 생성한다.
- 반복 템플릿의 `recurrence_type`은 `DAILY`, `WEEKLY`, `MONTHLY`로 제한한다.
- `recurrence_rule` JSON으로 특정 요일, 매월 특정 날짜, 실행 시각, 시작일, 종료일을 표현한다.
- 월간 반복일이 존재하지 않는 달에는 그 달의 마지막 날에 업무를 생성한다.
- 생성된 반복 업무는 `due_at = NULL`, 초기 상태 `WAITING`이다.
- `is_active = false`이면 이후 업무 생성을 중지한다. 이미 생성된 업무는 유지한다.
- 비활성 기간의 누락 회차는 템플릿 재활성화 후에도 생성하지 않는다.

### 예정 시각과 장애 보정

- `task.scheduled_for`는 반복 업무가 생성되도록 예정된 시각이다. 마감일이 아니다.
- 반복 업무의 중복 생성은 `UNIQUE (recurring_template_id, scheduled_for)`로 막는다.
- 서버 재시작 또는 스케줄러 장애 복구 시, 현재 시각 기준 최근 7일 안의 미생성 회차만 보정 생성한다.
- 최근 7일보다 오래된 회차는 생성하지 않는다.

### 특정 회차 건너뛰기

- 반복 업무의 특정 회차를 삭제하면 해당 회차만 영구적으로 건너뛴다. 이후 회차는 정상 생성한다.
- 업무 하드 삭제 후에도 스케줄러가 같은 회차를 다시 만들지 않도록 `recurring_task_skip`에 기록한다.
- 반복 업무 삭제와 `recurring_task_skip` 기록 저장은 하나의 Application 트랜잭션에서 처리한다.
- 동일한 `(recurring_template_id, scheduled_for)` skip 기록이 이미 있으면 중복 오류 없이 멱등적으로 처리한다.

| 컬럼 | 설명 | 제약 |
| --- | --- | --- |
| `recurring_template_id` | 반복 업무 템플릿 번호 | PK, FK |
| `scheduled_for` | 건너뛴 회차의 생성 예정 시각 | PK |
| `created_at` | 건너뛰기 기록 생성 시각 | |

```text
PK: (recurring_template_id, scheduled_for)
FK: recurring_task_skip.recurring_template_id
    → recurring_task_template.recurring_template_id ON DELETE CASCADE
```
