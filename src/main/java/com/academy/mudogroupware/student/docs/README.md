# student 모듈

> 학생 관리 화면과 Figma 시안 기준을 반영한 구현 문서다. 현재 student 패키지에는 학생 등록/수정/목록/상세 조회와 수강 등록/종료 백엔드가 포함되어 있다.

## 책임과 범위

학원에 등록된 학생 마스터 데이터와 학생별 수강 등록을 담당한다. 학생은 그룹웨어 로그인 계정이 아니며, `users` 모듈의 직원 계정과 분리된 별도 데이터다.

- **Student(학생)**: 이름/학년/학교/전화번호/학부모 전화번호/특이사항을 가진 학생 기본 정보. 로그인 계정은 만들지 않는다.
- **Enrollment(수강 등록)**: 특정 학생이 특정 강의를 수강 중이라는 연결 정보. 학생 상세에서 현재 수강 중인 강의 목록으로 보이고, 강의 상세에서도 수강생 목록으로 조회될 수 있어야 한다.
- **학생 탭**: 학생을 가나다순 행 목록으로 보고, 검색하고, 선택한 학생의 상세를 같은 화면에서 바로 확인하는 화면이다. 기본 구조는 좌측 상세 패널 + 우측 학생 목록 패널이다.
- **강의 등록 흐름**: 학생 상세 또는 학생 등록 후 강의를 선택해 수강 등록할 수 있다. 화면의 주요 버튼 이름은 **"결제하기"** 로 두지만, 이번 범위에서는 실제 카드 결제/POS 연동 없이 선택한 강의에 학생을 등록하는 동작까지만 처리한다.
- **결제 보류**: 실제 결제 처리, 카드 단말기/POS 연동, 결제 취소/환불, 미납 관리, 영수증 발급은 이번 범위가 아니다. 추후 `payment` 또는 별도 결제 연동 범위로 분리한다.

## 소유하는 주요 데이터와 상태

| 엔티티 | 주요 필드 | 비고 |
|---|---|---|
| `Student` | `academyId`, `name`, `grade`, `school`, `phone`, `parentPhone`, `note`, `createdAt`, `updatedAt`, `deletedAt` | 학생 마스터 데이터. `users`와 무관하며 로그인 계정이 없다. 삭제는 소프트 삭제(`deletedAt`)이며, 30일 경과 후 배치로 하드 삭제된다(아래 "삭제 정책" 참고). |
| `Enrollment` | `academyId`, `studentId`, `lectureId`, `enrolledAt`, `status`(enum: `ACTIVE`/`ENDED`) | 학생과 강의의 수강 연결. 같은 학생이 같은 강의에 중복 등록되지 않게 한다. |

모든 테이블에 `academyId`(멀티테넌시) 컬럼을 두고, 모든 조회·생성·수정 경로에서 요청자 학원 스코프를 검증한다.

### 정렬과 검색 정책

- 학생 목록 기본 정렬은 **가나다순**이다.
- 검색은 학생 이름을 우선으로 한다.
- Figma에서는 검색창을 우측 학생 목록 상단에 두고, 검색 결과도 동일한 행 목록 형태로 보여준다.
- 동명이인이 있을 수 있으므로 상세 진입 전 목록 행에는 최소한 이름/학년/학교/학부모 전화번호 일부를 함께 보여준다.
- 학생 목록에서 행을 선택하면 페이지 이동 없이 좌측 상세 패널 내용만 갱신한다.

### 수강 등록 정책

- 학생은 여러 강의를 동시에 수강할 수 있다.
- 같은 학생을 같은 강의에 중복 등록하지 않는다.
- `Enrollment.status=ACTIVE`이면 현재 수강 중으로 본다.
- 수강 종료/휴강/퇴원 처리는 추후 확장 가능하게 상태값을 두되, 이번 화면의 핵심 흐름은 학생 등록과 현재 수강 등록이다.

### 삭제 정책 (소프트 삭제 → 하드 삭제)

- `DELETE /api/students/{studentId}`는 `deletedAt`만 채우는 소프트 삭제다. 삭제 즉시 목록/상세/수정 조회에서 제외되지만 DB row와 수강 이력(`student_enrollment`)은 그대로 남는다.
- 소프트 삭제 후 **30일이 지난 학생**은 `global`의 공통 삭제 배치(`GlobalRetentionScheduler`, 매일 03:00 KST)가 자동으로 하드 삭제한다 — `student.application.retention.{StudentRetentionJob, StudentRetentionService, StudentRetentionProperties}`, `StudentRetentionAdapter`.
- 하드 삭제 순서: 수강 이력(자식) 먼저 삭제 → 학생(부모) 삭제. 삭제 시점에 `deletedAt < threshold` 조건을 다시 검사해, 후보 조회 이후 상태가 바뀐 경우(복구 등)를 방어한다.
- 보관 기간(30일)과 배치 크기(500)는 `StudentRetentionProperties` 기본값으로 관리하며 비밀값이 아니다. 설계 배경은 [global/docs/BOILER_PLATE.md](../../global/docs/BOILER_PLATE.md) 참고.

## 외부에 공개하는 Application API

학생 관리:
- `CreateStudentUseCase` — 학생 등록 (이름/학년/학교/전화번호/학부모 전화번호/특이사항)
- `UpdateStudentUseCase` — 학생 기본 정보 수정
- `StudentQueryUseCase` — 학생 목록(가나다순, 검색 포함) / 학생 상세(개인정보와 현재 수강 중인 강의 목록 포함) 조회

수강 등록:
- `EnrollStudentUseCase` — 학생을 선택한 강의에 등록. 화면에서는 "결제하기" 버튼을 누르는 흐름이지만, 이번 범위에서는 실제 결제 없이 수강 등록만 처리한다.
- `EndEnrollmentUseCase` — 수강 종료 처리. 구현 우선순위는 낮지만, `Enrollment.status` 변경 흐름으로 남긴다.

다른 모듈 조회용 공개 Port:
- `StudentRosterPort` — rollcall 모듈이 특정 강의의 출결부를 만들 때 수강생 이름/학년/학부모 전화번호를 조회하기 위한 Port. 아직 별도 Port 코드는 만들지 않았고, rollcall 구현 시 공개 계약으로 추가한다.
- `LectureStudentPort` — lecture 모듈이 강의 상세에서 수강생 목록을 보여줄 때 사용하는 Port. 아직 별도 Port 코드는 만들지 않았고, lecture 구현 시 공개 계약으로 추가한다.

## 다른 모듈 또는 외부 시스템에 요청하는 의존성

- **강의 목록 조회 — `lecture` 모듈에 요청 필요**: 학생을 강의에 등록하려면 선택 가능한 강의 목록과 강의 기본 정보(강의명/학년/시즌/과목/선생님/요일·시간/가격)를 조회해야 한다. student 모듈은 `lecture` 모듈의 공개 Port를 통해서만 조회하고, `Lecture` Entity/Repository를 직접 참조하지 않는다.

    ```text
    [대상 모듈] lecture

    [필요한 변경] 수강 등록용 강의 검색/조회 Port (예: LectureCatalogPort.search(academyId, filters))

    [입력] academyId, 검색 키워드 또는 필터(학년/과목/선생님/요일 등)

    [출력] lectureId, 강의명, 학년, 시즌, 과목, 선생님명, 요일·시간, 가격 방식, 가격

    [필요한 이유] 학생 상세/학생 등록 후 특정 강의를 선택해 수강 등록해야 함

    [영향 범위] student 모듈 학생 상세, 수강 등록 화면
    ```

- **결제 연동 — 추후 별도 범위**: 실제 카드 결제, POS/단말기 연결, 결제 취소/환불, 영수증 발급은 이번 범위에서 제외한다. 현재 "결제하기" 버튼은 수강 등록을 확정하는 임시 버튼명으로만 사용한다.
- **인증 사용자 정보**: `global.presentation.security.AuthUser` 사용.
- **권한**: 학생 개인정보와 학부모 연락처를 다루므로 학생관리 탭 접근부터 목록/상세 조회, 학생 등록/수정, 수강 등록/종료까지 `STUDENT:MANAGE` 하나로 관리한다. 실제 role에 권한을 매핑하는 `role_permission` 구성은 admin의 role 관리 화면 몫이라 student 모듈은 관여하지 않는다.

## 발행·소비하는 Event

- 아직 없음.
- 추후 실제 결제 연동이 붙으면 `EnrollmentCreatedEvent` 또는 결제 완료 이벤트 소비를 검토한다.
- 추후 강의 변경 알림, 수강 등록 알림이 필요해지면 기존 알림 정책과 맞춰 별도 Event 계약을 검토한다.

## 변경 시 주의 사항 / 설계 결정 배경

- **학생은 users 계정이 아니다.** 학생과 학부모는 그룹웨어 로그인 대상이 아니므로, 직원 계정 테이블과 분리한다.
- **학생 데이터 소유권은 student 모듈에 둔다.** lecture는 강의 자체를 소유하고, rollcall은 출결 기록을 소유한다. 학생 기본 정보와 수강 등록은 student 모듈이 소유한다.
- **결제는 이번 범위에서 영구적으로 구현하지 않는다(확정, 2026-08-06).** Figma에서는 "결제하기" 버튼을 유지하되 기능은 선택한 강의에 학생을 등록하는 것으로 제한한다. 필요해지면 별도 payment 모듈로 완전히 분리해 새로 설계한다.
- **강의 등록은 학생 화면에서도 가능해야 한다.** 사용자가 학생을 먼저 찾거나 새로 등록한 뒤, 그 학생을 바로 강의에 넣는 흐름이 핵심이다.

## 화면 구성 (Figma 참고용)

왼쪽 네비게이션에는 **"학생" 섹션 아래 "학생 관리" 탭**을 둔다. 학생 관리 화면은 페이지 이동형 상세가 아니라, 한 화면에서 조회하는 2패널 구조로 설계한다.

```text
학생
└─ 학생 관리   (기본 진입 화면)
```

### 1. 학생 관리

기본 화면은 **좌측 상세 패널 + 우측 학생 목록 패널**이다. 우측 목록에서 학생을 선택하면 좌측에 해당 학생의 상세 정보와 현재 수강 중인 강의가 즉시 표시된다. 상세 페이지로 이동하지 않고 같은 화면에서 계속 조회할 수 있어야 한다.

| 페이지 | 내용 |
|---|---|
| 학생 목록 패널(오른쪽) | 가나다순 학생 행 목록. 상단에 검색창을 두고 이름으로 빠르게 찾을 수 있게 한다. 각 행에는 학생명/학년/학교/학부모 연락처 일부/현재 수강 강의 수를 표시한다. 행 클릭 시 페이지 이동 없이 왼쪽 상세 패널이 갱신된다. |
| 학생 상세 패널(왼쪽) | 선택한 학생의 기본 정보 + 현재 수강 중인 강의 목록. 강의 목록에는 강의명/선생님/요일·시간/가격 방식/가격을 보여준다. 상단 또는 강의 목록 영역에 "+ 강의 등록" 버튼을 둔다. 아직 선택한 학생이 없으면 빈 상태 또는 첫 번째 학생 선택 상태로 보여준다. |
| 학생 등록 | 이름/학년/학교/전화번호/학부모 전화번호/특이사항 입력. 저장 후 왼쪽 상세 패널에 새 학생 정보가 표시되고, 이어서 강의 등록을 할 수 있게 한다. |
| 강의 등록/결제하기 | 왼쪽 상세 패널에서 강의를 검색해 선택한다. 선택 후 **"결제하기"** 버튼을 누르면 실제 결제 없이 해당 강의에 학생이 수강 등록된다. 버튼명은 추후 실제 결제 연동을 고려해 유지한다. |

### 2. 보류 기능

| 기능 | 이번 범위 처리 |
|---|---|
| 카드 결제 | 보류. "결제하기" 버튼은 수강 등록 확정 동작만 수행 |
| POS/단말기 연동 | 보류 |
| 환불/결제 취소 | 보류 |
| 미납/수납 관리 | 보류 |
| 영수증 발급 | 보류 |
